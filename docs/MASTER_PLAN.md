# DentVision — мастер-план разработки

**Версия:** 1.0  
**Дата ревизии:** 2026-10-25  
**Базовая ветка анализа:** main  
**Цель:** довести текущую реализацию DentVision до стабильной, безопасной, проверяемой SaaS-платформы и затем построить Control Center владельца без переписывания работающих модулей без необходимости.

> Этот документ — источник истины для последовательности разработки. Функция не считается готовой только потому, что для неё существует экран или компонент. Готовность подтверждается работающим сценарием, серверной проверкой прав, сохранением данных и тестами.

## 1. Правила разработки

1. Перед каждым этапом читать этот мастер-план, README, архитектурные документы и относящиеся к задаче исходники.
2. Сначала исследовать текущую реализацию и зависимости. Не создавать параллельный модуль, если уже существует подходящий.
3. Не переписывать приложение целиком. Рефакторинг — небольшими проверяемыми изменениями.
4. Не считать мок, демонстрационные цифры, локальный state или setTimeout реализацией бизнес-функции.
5. Не выполнять изменения с необратимыми последствиями без плана миграции, резервной копии и проверяемого отката.
6. Не выводить медицинские, персональные, финансовые данные и секреты в клиентские логи, AI-запросы или аудит без обоснованной необходимости и разрешения.
7. Не помещать секретные ключи и учётные данные в браузерный код. Публичный Supabase publishable key может быть в клиенте только при правильно настроенных серверных политиках; административные полномочия на нём не строятся.
8. Каждый этап заканчивается проверками и записью результата: изменённые файлы, тесты, известные ограничения, миграции и следующий шаг.
9. Не отмечать этап выполненным без фактического подтверждения. Если проверка невозможна из-за отсутствия доступа к окружению или базе данных — фиксировать это как блокер.
10. Работать только в согласованном репозитории и ветке. Не менять production-данные для тестирования.

## 2. Состояние кода на момент ревизии

Активная точка входа Vite — index.html → src/index.jsx → src/App.jsx. Корневой файл dentvision-saas.jsx содержит отдельную монолитную реализацию и не должен автоматически считаться идентичным активному приложению. Его назначение нужно установить до удаления или переноса кода.

### Уже присутствует в репозитории

- React 18 + Vite; базовые UI-компоненты и общие константы.
- Основная навигационная оболочка приложения.
- Экраны входа/регистрации, Dashboard, расписания, пациентов, кассы/финансов, лаборатории, AI-команды и Super Admin.
- Компонент 3D-одонтограммы.
- Клиентский слой Supabase RPC и функции для отдельных операций с пациентами, записями, лечением, платежами, фото, лабораторными заказами, расходами, складом, долгами и подписками.
- Хуки состояния и загрузки данных, отдельные диагностические функции подключения.
- Черновая интеграция AI с четырьмя ролями ассистентов.
- UI для некоторых функций: одонтограмма, фотопротокол, финансовые вкладки, лабораторные заказы, управление клиниками.

Эти пункты означают наличие кода или интерфейса, а не подтверждённую производственную готовность.

### Что нельзя пока заявлять готовым

- Регистрация организации и создание учётной записи в рабочей среде.
- Надёжная изоляция данных разных клиник и серверная авторизация ролей.
- Реальные значения всех дашбордов и финансовых отчётов.
- Постоянное хранение фотографий.
- Работающее подключение к WhatsApp Business API.
- Реальные AI-агенты с доступом к данным и инструментам.
- Полноценная панель владельца с действующими серверными операциями.
- Резервное копирование и восстановление, мониторинг, production-релиз.

Для этих функций есть отдельные клиентские вызовы, UI или заготовки, но наличие клиентского кода не подтверждает работающую серверную реализацию.

## 3. Целевая архитектура и полномочия

Архитектурный принцип: один продукт с отдельными рабочими пространствами, единым серверным слоем и строгим разделением прав.

### Контуры доступа

1. **Владелец платформы** — глобальные организации, тарифы, системные конфигурации, финансовые показатели платформы и критические разрешения.
2. **Операционный администратор платформы** — техническая диагностика и сопровождение в пределах выданных разрешений.
3. **Финансовый менеджер платформы** — расчёты подписок, сверки, возвраты и отчётность; без доступа к медицинским картам.
4. **Поддержка** — обращения, диагностика и ограниченный временный доступ по обоснованной заявке.
5. **Менеджер по клиникам** — только закреплённые организации и разрешённые коммерческие данные.
6. **Администратор / управляющий клиники** — сотрудники, расписание и операционные настройки своей организации.
7. **Врач / ассистент / кассир / бухгалтер / сотрудник лаборатории** — минимально необходимый набор действий по должности и филиалу.
8. **AI-агент** — отдельная машинная идентичность с явным списком разрешённых инструментов, ресурсов, лимитов и действий.

Роли должны строиться поверх разрешений. Минимальные уровни действий: read, create, update, delete, export, approve, execute. Права применяются на сервере, а не только через скрытие пунктов меню.

### Основные технические принципы

- Каждая бизнес-запись связана с организацией/клиникой и, где необходимо, с филиалом.
- Tenant scope проверяется сервером по аутентифицированной сессии; нельзя доверять clinic_id, переданному браузером.
- Секретные операции выполняются на сервере через проверяемые функции/API.
- Аудит критических действий неизменяем и сам не редактируется обычными администраторами.
- Для операций с риском потери данных обязательны подтверждение, идемпотентность и понятный результат.
- Медицинские изображения и документы хранятся в закрытом хранилище с проверкой доступа.
- Ошибка backend не маскируется локальным успешным toast.
- Все важные изменения имеют тесты, миграцию и план отката.

## 4. Последовательность реализации

**Приоритет: P0. До новых крупных функций.**

- [ ] Получить и записать фактическую команду сборки и результат npm run build.
- [ ] Проверить, что активный Vite entrypoint — модульное src-приложение; отметить роль монолитного dentvision-saas.jsx.
- [ ] Получить безопасный доступ к актуальной схеме Supabase, RPC-функциям, RLS-политикам, storage policies и текущим миграциям.
- [ ] Снять baseline основных пользовательских сценариев и ошибок консоли/сети в тестовой среде.
- [ ] Составить карту таблиц, RPC, хуков, страниц и операций CRUD.
- [ ] Установить, какие тестовые данные существуют только в коде, а какие реально хранятся в базе.
- [ ] Создать тестовую среду без production-данных и определить резервное копирование перед миграциями.

**Готово, когда:** есть повторяемая сборка, схема backend доступна для ревизии, список блокеров подтверждён, production-данные не используются для экспериментов.

### Этап 1 — Восстановить приложение и единый поток авторизации

**Приоритет: P0.**

- [ ] Спроектировать единый AuthProvider/контекст или эквивалентный общий слой состояния.
- [ ] Согласовать интерфейс login/register/logout/session restore и загрузку профиля организации.
- [ ] Устранить несовпадения аргументов Login/useAuth и отсутствие register.
- [ ] Обеспечить, чтобы App получал один и тот же user, clinic, loading, logout во всех страницах.
- [ ] Проверять состояние сессии при перезагрузке и корректно завершать её при logout.
- [ ] Добавить обработку ошибок входа, истёкшей сессии и недоступности backend.
- [ ] Удалить из производственного потока жёстко заданную глобальную учётную запись и демонстрационные пароли.
- [ ] Реализовать безопасный сценарий создания первой учётной записи владельца вне публичной регистрации.
- [ ] Проверить, что прямая навигация на страницу не обходит авторизацию.

**Тесты:** успешный и неуспешный вход, logout, перезагрузка страницы, истёкшая сессия, регистрация, отказ при отсутствии прав.

**Готово, когда:** базовые сценарии авторизации проходят end-to-end, контекст пользователя не расходится между компонентами, защищённые страницы недоступны без сессии.

**Приоритет: P0.**

- [ ] Описать и сохранить SQL-миграции схемы и серверных функций в репозитории.
- [ ] Сопоставить каждый RPC-вызов с реальным определением функции, параметрами, ответом и проверкой прав.
- [ ] Зафиксировать типы основных сущностей: clinics/organizations, users, patients, appointments, treatments, receipts/payments, expenses, inventory, subscriptions, lab_orders, photos, audit_events.
- [ ] Перепроектировать useData: явные данные, loading, error, refresh и CRUD-методы, без универсального хука, возвращающего только пациентов.
- [ ] Согласовать контракты useLabOrders, useSubscription и usePhotoProtocol с фактическим использованием страниц.
- [ ] Добавить стабильные идентификаторы, валидацию полей, обработку повторных запросов и согласованное отображение ошибок.
- [ ] Устранить потерю состояния при перезагрузке и некорректное предположение об успешной записи.
- [ ] Добавить пагинацию/фильтрацию на сервере для потенциально больших списков.

**Тесты:** CRUD по каждой сущности; отказ при ошибке сети; повторное сохранение; пустой ответ; неверные поля; конкурентные изменения; отсутствие случайного удаления.

**Готово, когда:** каждая используемая страницей операция поддерживается реальным серверным контрактом и проверена на тестовой базе.

**Готово, когда:** тесты изоляции проходят для REST, RPC, файлов и всех используемых каналов доступа.
